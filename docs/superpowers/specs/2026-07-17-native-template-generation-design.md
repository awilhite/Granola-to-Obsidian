# Native Granola Template Generation

## Summary

Replace Granola Template Management's legacy generation sequence with Granola's current native summary-generation flow. The plugin currently calls `llm-proxy-stream`, receives Markdown, creates a panel, and writes that Markdown directly through `update-document-panel`. Granola stores that direct write as one collapsed ProseMirror paragraph, which causes malformed formatting in Granola and Obsidian.

The replacement creates the selected template panel and calls `generate-summary` with the panel ID, template ID, prompt variables, and a seeded Yjs document. Granola then persists HTML, structured ProseMirror content, and Yjs state itself. Template-generation failure remains non-blocking for the overall sync.

## Evidence And Graduation

The supervised spike on the July 17, 2026 `Testing` meeting proved the load-bearing assumption:

- the selected `Default` template was absent before the call
- the source document had a finalized transcript
- `generate-summary` emitted `panel_id`, content deltas, generated lines, and Yjs state
- the persisted panel matched the configured template ID
- `original_content` was HTML
- panel content contained structured paragraph, heading, and bullet-list nodes
- the document and panel timestamps changed
- the panel was visible through the Granola API

This observation graduates `generate-summary` from spike to implementation. Synthetic transcript creation is not part of the feature; the plugin operates only on existing Granola documents and transcripts.

### Compatibility Validation Update (2026-07-17)

On disposable document `6f01045f-be6e-4492-b370-8f4e6fdfacca`, native generation succeeded with `auto: false`. A scheduled plugin cycle and a sanitized direct probe both received HTTP 409 with `auto: true`; cleanup succeeded. Therefore every user-configured Template Management generation request must send `auto: false`, even when the plugin sync source is automatic. The configured plugin scheduler remains automatic because this private request field represents Granola background-generation eligibility, not the plugin's sync source. Generic orchestration failures may log only a numeric HTTP status or `unknown`; they must not log response bodies, messages, titles, transcripts, generated content, or credentials.

## Goals

- Make automatically applied templates structurally equivalent to templates generated by Granola.
- Preserve automatic behavior in manual and scheduled sync.
- Ensure a failed generation can retry on a later sync.
- Continue normal Obsidian sync when template generation fails.
- Keep legacy malformed-summary normalization for previously damaged panels.
- Make generation outcomes visible in existing template-management diagnostics.

## Non-Goals

- Do not change template selection or settings UX.
- Do not modify Granola authentication beyond using the current resolved credentials.
- Do not reverse-engineer transcript insertion or create Granola documents.
- Do not add managed Obsidian note updates.
- Do not fall back to the legacy Markdown generation path.
- Do not remove the existing legacy normalization fixtures or behavior.

## Approaches Considered

### Native-only generation

Create the panel, invoke `generate-summary`, and verify Granola's persisted structured result. After failure, delete only the exact plugin-created panel that a private re-fetch proves is active and empty; preserve ambiguous or populated panels.

This is the selected approach because it follows the observed current Granola flow and cannot silently recreate the known malformed storage shape.

### Native generation with legacy fallback

Try `generate-summary`, then run `llm-proxy-stream` and direct Markdown writeback if it fails.

This is rejected because availability would come at the cost of silently creating malformed panels. The configured template would appear present, preventing an automatic retry.

### Keep legacy generation and improve Markdown conversion

Convert generated Markdown into ProseMirror JSON inside the plugin before writing it.

This is rejected because Granola already owns the HTML, ProseMirror, generated-lines, and Yjs conversion. Reimplementing that private representation would be more brittle than using Granola's native endpoint.

## Design

### Granola client contract

Replace `generateTemplateMarkdown` with a native generation operation that accepts:

- source document
- document metadata
- transcript entries
- selected template
- created panel ID

The operation sends one request to `https://stream.api.granola.ai/v1/generate-summary` with:

- `document_id`
- `panel_id`
- `panel_title`
- `prompt_slug: template-summary-consolidated`
- existing `prompt_variables`
- empty `chat_history`
- selected template ID as `template_slug`
- a minimal base64 Yjs seed as `ydoc_state`
- `ydoc_version: 1`
- `auto: false`, regardless of manual or scheduled plugin sync source

The stream parser records event classes without depending on generated prose. Stream events are telemetry only; persisted panel state is the sole source of truth because the server may complete persistence even when the client does not observe every event.

### Sync sequence

For a document missing the selected template:

1. Before the `changed` up-to-date decision, accept a populated matching panel embedded in the normal document response as the cheap ready path; privately verify missing or ambiguous candidates. Existing notes using `never` bypass Template Management entirely.
2. If the per-run generation budget remains, fetch templates, source document, metadata, and transcript as today. Generate at most one new panel per sync run; defer additional missing candidates without failing normal sync.
3. Create an empty panel for the selected template.
4. Call native generation using the returned panel ID.
5. Poll `get-document-panels` for the created panel until it has `content_updated_at` and structured content.
6. Refresh the source document and choose the newest valid timestamp among the original document, verified panel, and refreshed document before the normal update decision.
7. Expose the persisted panel content through the existing rendering path.

The existing-template path remains unchanged and never regenerates an active matching panel.

### Success criteria

Generation succeeds only when the refreshed panel:

- is not deleted
- matches the selected template ID
- has `content_updated_at`
- contains a ProseMirror document object with content nodes
- has non-empty Yjs state when requested by the verification fetch

The plugin must use the refreshed panel rather than streamed text when constructing the Obsidian note.

### Failure and retry

If panel creation succeeds but generation or verification fails, privately re-fetch the created panel. Delete it only when the exact plugin-created panel is active and definitely empty. Preserve ambiguous, missing-from-response, or populated panels; cleanup uncertainty must not destroy content or hide the original generation error. Once structured persisted content is verified, a later document-refresh failure never deletes that panel.

The plugin then:

- increments template-management failure diagnostics
- logs only safe stage context and a numeric HTTP status or `unknown`, without document titles, transcript, generated content, response bodies, or credentials
- continues normal sync with the source content already available

No legacy generation fallback runs. A safely deleted empty panel is retryable on a later sync. Preserved empty panels follow the existing in-progress/stale policy, while ambiguous or populated panels are deferred rather than destructively retried. Each sync run can generate at most one new panel, so other missing candidates are `template-deferred` until a later run.

### Legacy normalization

Keep `normalizeMalformedSummaryMarkdown` and its fixtures for panels previously written by the old flow. New native generation must not route streamed HTML through this normalizer or directly write generated Markdown.

## Operability

### Liveness

Assumption: Granola's private API and streaming endpoint are reachable while sync runs.

Policy: time-bound generation and verification; recover by continuing normal sync and retrying later. Surface failure in diagnostics and console logs.

### Credentials

Assumption: the existing auth resolver supplies a current access token, workspace ID, device ID, and client headers.

Policy: use the existing refresh-aware client path. Auth failures remain visible and do not trigger a legacy fallback.

### Version and contract change

Assumption: `generate-summary`, stream event shapes, and Yjs version 1 remain compatible.

Policy: parse events defensively and verify persisted panel shape. A contract mismatch fails closed for template generation while normal sync continues.

### Concurrency

Assumption: only one plugin sync run processes a document at a time, but Granola or another client may create the panel concurrently.

Policy: retain the plugin's sync-run guard, check before creation, and re-fetch after generation. Never create a second panel when a matching active panel is observed.

### Observability

Policy: retain attempted, applied, failed, skipped, and deferred counters. Add stage-specific failure context and generation/verification duration without logging document titles, transcript text, generated prose, response bodies, tokens, or credentials. Silent failure is not acceptable.

## Testing

### Automated tests

- Native request contains the selected template ID, panel ID, Yjs seed, and current prompt variables.
- Stream parsing recognizes panel, content, generated-lines, and Yjs events.
- Existing matching panel skips creation and generation.
- Successful verification uses persisted structured panel content.
- Generation failure deletes the newly created panel only after a re-fetch proves it is active and empty; ambiguous or populated panels are preserved.
- Verified populated panels survive document-refresh failure and retain the newest valid source/panel/refresh timestamp.
- Process-level coverage confirms `changed` checks templates before skipping, `never` bypasses template work, and one generation per run defers additional missing candidates.
- Cleanup failure preserves the original failure result and reports cleanup separately.
- Legacy malformed-summary tests continue passing.
- Auth and API-client regression tests continue passing.

### Controlled live validation

1. Create a Granola meeting with a finalized transcript and no selected Default panel.
2. Run manual sync and confirm one structured Default panel appears in Granola.
3. Confirm the Obsidian meeting note has correct headings, lists, metadata, authored notes, and transcript behavior.
4. Run sync again and confirm generation is skipped.
5. Run one scheduled five-minute sync on another eligible meeting without user interaction.
6. Confirm no new Obsidian errors and inspect template-management diagnostics.

### Failure validation

Use injected client failures in automated tests rather than corrupting a live meeting. Confirm a re-fetched definitely empty plugin-created panel is deleted, while verified, populated, or ambiguous panels are preserved and the document continues through normal sync.

## Rollout

Implement on `codex/native-template-generation`, run automated tests and the controlled validation, then review the complete branch stack before merging it into `main`. Merging remains a separate user decision.

## Decision

Use Granola's native `generate-summary` flow as the only automatic template-generation path. Preserve legacy normalization only for existing malformed panels, and prefer retryable failure over malformed fallback output.
